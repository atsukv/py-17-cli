# Log Analyzer

***

***CLI-утиліта для аналізу серверних логів та збору статистики.***

***

## Plan

1. **Підготовка:** Спочатку ми генеруємо великий файл логів (на 200 000 рядків) за допомогою окремого скрипта.
2. **Запуск:** Програма вітається, показує підказку `help` і починає постійно чекати на команди від користувача.
3. **Аналіз даних:** Коли ви вводите валідну команду (наприклад, `summary` або `top ip 5`), програма читає лог-файл по
   одному рядку. Правильні дані вона бере в роботу, а "биті" рядки просто рахує і пропускає, щоб зекономити пам'ять.
4. **Вивід та збереження:** Результати аналізу програма одразу показує на екрані, а за бажанням їх можна зберегти у файл
   командою `export`.
5. **Захист від помилок:** Якщо ввести неіснуючу команду або зробити одруківку, програма не вилітає. Вона спокійно
   повідомить про помилку і чекатиме на наступну команду.
6. **Завершення:** Програма працює доти, поки користувач не введе команду `quit`.

## How to run

Якщо ще не було згенеровано файл логу access.log, то генеруємо його

```
python make_sample_log.py number
```

* python — звертаємось до Python, щоб передати йому файл;
* make_sample_log.py — викликаємо готовий модуль для генерації логу в форматі .log;
* number — число для генерації логу, будь-яке ціле число, крім 17.

Для свого проекту я зробив таку генерацію

```
$ python make_sample_log.py 249
access.log: 200000 lines, seed 249
```

Розбір даних файлу лог який приймає програма

```
Ось як виглядає типовий рядок нашого логу:
2026-10-01T00:00:02 10.6.9.183 GET /static/style.css 200 529

Якщо розбити його по пробілах за допомогою .split(), ми отримаємо такі елементи майбутнього словника:

2026-10-01T00:00:02 — час та дата (timestamp)
10.6.9.183 — IP-адреса клієнта (ip)
GET — HTTP-метод запиту (method)
/static/style.css — той самий «шлях» або шлях запиту (path)
200 — статус відповіді сервера (status)
529 — розмір переданих даних у байтах (size)
```

## Commands

Після запуску програми доступні такі команди:

* `help` — виводить список доступних команд, а також інформацію по них;
* `summary` — вираховує кількість рядків в файлі;
* `top` — показує топ елементів за заданої кількості в конкретній категорії (*top \<category\> \<counts\>:* `top ip 5`,
  `top status 7`, `top size 10`);
* `export` — зберігає виконання команди в файл (*export \<filename\>*: `export`, `export my_log`);
* `quit` — завершення роботи програми.

## Design decisions

### 1. Аналіз пошкоджених рядків

Мій файл містить **2009** помилкових рядків.

Приклади з мого запуску команди `summary`:

1. `'2026-10-01T00:04:41 10.5'`
2. `'2026-10-'`

**Чому вони є помилковими:**

В обох випадках ми бачимо, що дані неповні. Програма очікує, що кожен валідний рядок логу складатиметься рівно з 6
аргументів (дата, IP, HTTP-метод, шлях, статус, розмір). Якщо розбити ці рядки за допомогою методу `.split()`, у першому
випадку ми отримаємо лише 2 елементи, а в другому — всього 1. Оскільки умова наявності 6 елементів не виконується,
програма коректно відхиляє ці рядки та записує їх у список пошкоджених.

### 2. Ручна перевірка

Створив файл `sample.log` з рядками з основного логу.

Команда `summary` вивела число **11** (загальна кількість рядків у файлі `sample.log`).

Щоб перевірити це вручну, я відкрив файл `sample.log`, і просто порахував усі існуючі
рядки зверху донизу. Їх виявилося рівно 11, що повністю збігається з результатом роботи моєї програми.

## AI log

У цьому проєкті я використовував ШІ як свого персонального ментора (без генерації готового коду). Він підказував мені,
коли я не міг вирішити проблему, та допомагав оформлювати проєкт професійніше.

### Головні проблеми, які ми вирішили:

1. **Модульність:** Розглянули загальну концепцію, щоб я зрозумів, як правильно розбити програму на три незалежні модулі
   (`main.py`, `logic.py`, `storage.py`).
2. **Оптимізація пам'яті:** Я написав базове зчитування файлу, а ментор підштовхнув мене до використання генераторів
   (`yield`). Це дозволило читати величезні логи по одному рядку без перевантаження пам'яті.
3. **Обробка винятків:** Програма вилітала, якщо файлу не існувало. Я розібрався з винятками, додав `try-except` для
   `FileNotFoundError` та навчився безпечно працювати з `.split()`.
4. **Баги з аргументами:** У мене зламалася команда `top ip 3` (програма сприймала слово "ip" як назву файлу). Ментор
   нагадав про різницю між позиційними та іменованими аргументами, після чого я успішно виправив помилку.

### Features I chose

- ***Функція 4. Три модулі*** (`main.py`, `logic.py`, `storage.py`)

> Розбиття проєкту на файли допомогло мені легше орієнтуватися в коді та швидше знаходити потрібні функції.

- ***Функція 6. Конвеєр генераторів*** (`storage.py`, `open_file`)

> Генератор (`yield`) читає величезний лог безпечно — по одному рядку за раз. Це рятує оперативну пам'ять комп'ютера від
> перевантаження.

- ***Від чого я відмовився***

> Відмовився від collections.Counter та enumerate, щоб реалізувати підрахунок для top вручну.
> Використання словника та
> .get() дозволило мені розібратися в алгоритмі.
